# Формат ошибок API

Любая ошибка бэкенда возвращается в одном формате. Фронтенду не нужно разбирать
разные виды ответов: достаточно один раз написать обработку.

## Пример

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Проверьте заполнение полей",
  "timestamp": "2026-11-17T08:15:30.123Z",
  "fields": [
    { "field": "name", "message": "не должно быть пустым" }
  ]
}
```

Если ошибка не про конкретные поля, `fields` приходит пустым списком:

```json
{
  "code": "NOT_FOUND",
  "message": "Шаблон не найден",
  "timestamp": "2026-11-17T08:15:30.123Z",
  "fields": []
}
```

## Поля ответа

| Поле | Тип | Описание |
|---|---|---|
| `code` | строка | Машинный код ошибки. По нему фронтенд выбирает поведение. Стабилен, не меняется |
| `message` | строка | Текст для пользователя, на русском. Можно показывать как есть |
| `timestamp` | строка | Время ошибки, ISO 8601, UTC |
| `fields` | массив | Ошибки по полям формы: `field` (имя поля в запросе) и `message`. Пустой, если ошибка не про поля |

## Коды ошибок

| HTTP | `code` | Когда возвращается |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Поля запроса не прошли проверку. Подробности в `fields` |
| 400 | `MALFORMED_REQUEST` | Тело запроса не разобрать (например, битый JSON) |
| 400 | `INVALID_PARAMETER` | Параметр пути или запроса неверного типа (например, `/api/templates/abc` вместо числа) |
| 400 | другой код | Бизнес-ошибка с собственным кодом (например, неверный формат файла импорта) |
| 403 | `FORBIDDEN` | Недостаточно прав для действия |
| 404 | `NOT_FOUND` | Объект не найден |
| 404 | `HTTP_404` | Такого адреса в API нет |
| 405 | `HTTP_405` | Для адреса использован неподдерживаемый метод (например, `DELETE` вместо `POST`) |
| 409 | свой код | Конфликт (например, клиент с таким email уже есть) |
| 409 | `TEMPLATE_ARCHIVED` | Попытка изменить архивный шаблон |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка сервера. Подробности в логах, пользователю показывать общий текст |

Для стандартных ошибок HTTP, которые не перечислены выше, код имеет вид `HTTP_<статус>`.
Новые бизнес-коды добавляются по мере появления правил, список ведётся в этой таблице.

Ошибка 401 (не вошли в систему) пока не описана: она появится вместе со входом.

## Как использовать на фронтенде

1. Ориентироваться на `code` и HTTP-статус, а не на текст `message`.
2. `VALIDATION_ERROR`: пройти по `fields` и показать каждое сообщение у своего поля формы по имени `field`.
3. Прочие ошибки: показать `message` общим сообщением.
4. `INTERNAL_ERROR` и любой неожиданный ответ (не JSON, нет `code`): показать общий текст «Что-то пошло не так, попробуйте позже».

## Как использовать на бэкенде

- Бизнес-ошибку бросать через `ApiException`, например `ApiException.notFound("Шаблон")`,
  `ApiException.conflict("EMAIL_TAKEN", "Клиент с таким email уже есть")`.
  Обработчик сам превратит её в ответ этого формата.
- Валидацию входных данных делать аннотациями (`@NotBlank`, `@Size`, `@Email`) на DTO и `@Valid`
  в контроллере. Ошибки полей превратятся в `VALIDATION_ERROR` автоматически.
- Свои ответы с ошибками вручную не собирать.

Реализация: пакет `com.mailforge.backend.common` (`ApiError`, `ApiException`, `GlobalExceptionHandler`).
